# spring: Spring Boot 4.1 (Spring MVC + Thymeleaf, embedded Tomcat), no caching

The Java version of `../nextjs`, `../sveltekit` and `../astro`. It has the same pages, markup and CSS (`../SPEC.md`,
`../shared/styles.css`). Every page is rendered on the server on every request from a fresh API call, in one JVM
process (`java -jar app.jar`). Pages ship **zero JS**: forms post and redirect back, like the Astro variant.

Versions: Spring Boot **4.1.1** (Spring Framework 7.0.9, Tomcat 11.0.24, Thymeleaf 3.1.5 via `thymeleaf-spring6`,
Jackson 3.1.5), JDK **25** LTS (Temurin 25.0.4.1), Maven 3.10.0 (wrapper 3.3.4). The project was generated by
start.spring.io (Maven, Java 25, dependencies `web` + `thymeleaf`, which in Boot 4 means
`spring-boot-starter-webmvc` + `spring-boot-starter-thymeleaf`). No Spring Security, no devtools, no actuator.

## How it renders

- **Tomcat, thread per request.** Spring Boot's embedded Tomcat (NIO connector) hands each request to a worker
  thread from its pool (defaults: max 200 threads, min 10 spare, 8192 max connections, accept queue 100). The worker
  runs the controller, which **blocks** on the API call (`RestClient` → JDK `HttpClient`), then renders the template
  on the same thread. Virtual threads are off by default in Boot 4.1 (`spring.threads.virtual.enabled=false`) and are
  left off, so these are platform threads (`http-nio-…-exec-N`). Concurrency is bounded by the pool, not an event loop.
- **Thymeleaf.** Templates are natural HTML with `th:*` attributes. With the production default
  `spring.thymeleaf.cache=true`, each template is parsed once (by the AttoParser) into a cached event model; that
  caches the *template*, not data. On every request the engine walks that model, evaluates the SpEL expressions
  (`${post.author}`, `th:each`, fragment calls) against the request's model and writes the HTML. `th:text` escapes
  text (a body of `<post> & check` renders as `&lt;post&gt; &amp; check`). There is no streaming and no hydration
  data; the writer goes through Tomcat's 8 KB response buffer, so pages arrive with `Transfer-Encoding: chunked`.
- **No caching.** No `@Cacheable`, no HTTP caching headers on pages. A post created directly on the API appears at
  the top of `/` on the next request.
- **Dates.** The JS variants use `Intl.DateTimeFormat("en", {dateStyle: "medium", timeStyle: "short", timeZone: "UTC"})`
  and append `" UTC"` (`Dec 31, 2025, 11:59 PM UTC`). Java's localized `FormatStyle.MEDIUM/SHORT` puts a narrow
  no-break space (U+202F) before `PM`, so an explicit pattern is used; the output has no U+202F. The `datetime`
  attribute is the raw `created_at`.
- **API client.** `RestClient` is built directly on a JDK `HttpClient` pinned to HTTP/1.1, which pools and reuses
  keep-alive connections. Two notes: in Boot 4 the auto-configured `RestClient.Builder` lives in the separate
  `spring-boot-restclient` module, which a Spring Web + Thymeleaf app doesn't include; and the JDK client defaults to
  HTTP/2, which on `http://` would add an `Upgrade: h2c` attempt on every new connection (Node's fetch speaks
  HTTP/1.1).

## Mutations and origin check

- The like form (on every post card) posts to `/actions/like` with a hidden `id`; the compose form posts to
  `/actions/create`; the login form posts to `/login`. Each answers **303** (Post/Redirect/Get): like goes back to the
  same-origin `Referer` path (else `/`), create to `/` or to `/?error=<API message>` when the API rejects the post
  (e.g. `body is required`), and both go to `/login` without a `token` cookie. Same scheme as Nuxt and Angular.
- Login signs `{"alg":"HS256","typ":"JWT"}` / `{"sub":"<id>","username":"<name>","iat":…,"exp":iat+7d}` with
  `JWT_SECRET` and sets it as `token` (`HttpOnly; SameSite=Lax; Path=/`). The header decodes the payload per request
  (not verified, like the other variants); the API verifies it.
- **Origin check**: Spring Web has no CSRF protection without Spring Security, so the three form routes apply the
  Next.js server-action rule (as the Nuxt and Angular variants do): if an `Origin` header is present, its host[:port]
  must equal the `Host` header, otherwise **403**. Works on any host with no build-time config. The `/api` JSON routes
  are not checked.
- `/api/posts` reads the raw body and parses it strictly with Jackson 3 (`readTree`: an empty body, truncated JSON
  or trailing garbage gives 400 `{"error":"malformed JSON body"}`), takes `String(body ?? "")` and sends
  `{"body": …}`. Both `/api` routes forward `Authorization` as-is (or none) and return the API's status and body
  bytes unchanged with `Content-Type: application/json`.

## JVM in a 1 vCPU / 2 GB container

No JVM flags are set. Temurin 25's container ergonomics (measured with `--cpus 1 --cpuset-cpus 16 --memory 2g`):
`UseSerialGC=true` (fewer than 2 CPUs means no "server-class machine", so not G1), `MaxHeapSize` 512 MB
(`MaxRAMPercentage=25`), `InitialHeapSize` 32 MB, `CICompilerCount=2`, tiered JIT on, 240 MB reserved code cache.

- **Startup**: about 4.7 s to "Started Application" (first 200 after about 7 s, including JVM start) on 1 CPU; about
  1.9 s on 4 CPUs. Hence the healthcheck's `--start-period=30s`.
- **Memory**: about 130 MiB container memory idle after startup, about 145 MiB after a couple of hundred requests
  (RSS about 170 MB), 34 threads (10 Tomcat workers + JIT/GC/JDK threads). This is the JIT-compiled-on-demand cold
  state; the heap grows toward its 512 MB cap under load.

## Differences from the JS variants

- **Payload.** Feed page about **10.5 KB**, post page about **1.0 KB**, 404 page 590 bytes, plus a separate
  `/styles.css` (3,789 bytes, `Last-Modified`, no `cache-control`, no ETag). No hydration data, no scripts. Thymeleaf
  keeps the template's whitespace as written.
- **Headers on pages**: `Content-Type: text/html;charset=UTF-8`, `Content-Language: en-US`,
  `Transfer-Encoding: chunked`. No ETag, no `cache-control`, no `x-powered-by`.
- **No compression** (`server.compression.enabled` defaults to false; responses had no `Content-Encoding` even with
  `Accept-Encoding: gzip, br`). No HTTP/2.
- **404s are real and HTML** for every client: missing post, invalid id (the API's 400) and unknown paths (Spring's
  `NoResourceFoundException` → Tomcat error dispatch → `NotFoundController`). Boot's default error controller would
  answer non-browser clients (curl) with JSON; this one always renders the not-found page, with the header.
- **JIT warm-up.** The first requests after startup run interpreted/C1 code and are slower until C2 kicks in.

## Build and run

Host has no JDK; everything runs in pinned containers.

```bash
# build (tests: one context-load test)
docker run --rm --user $(id -u):$(id -g) -e HOME=/tmp -v ~/.m2:/m2 -v $PWD:/app -w /app \
  --entrypoint ./mvnw maven:3.10.0-eclipse-temurin-25 -B -Dmaven.repo.local=/m2/repository package
# run
docker run --rm --network host -e HOST=127.0.0.1 -e PORT=3000 -e BACKEND_URL=http://127.0.0.1:4000 \
  -v $PWD/target/spring.jar:/app/app.jar:ro eclipse-temurin:25.0.4.1_1-jre java -jar /app/app.jar
```

The Dockerfile builds `target/spring.jar` with `maven:3.10.0-eclipse-temurin-25` and runs it on
`eclipse-temurin:25.0.4.1_1-jre` (plus `iproute2` and `curl`), applies the optional `NET_DELAY` with `tc netem`,
listens on `0.0.0.0:3000` and health-checks with `curl -sf http://127.0.0.1:3000/`. Env: `BACKEND_URL` (default
`http://127.0.0.1:4000`), `JWT_SECRET` (default `twelve-dollar-challenge`), `HOST`/`PORT` (default `127.0.0.1:3000`
outside Docker).
