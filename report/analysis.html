How many users can a frontend framework serve on a $12 server?

stacks rendered the same small feed site against the same Rust + SQLite API. Each got a 1-core-sized box (throttled to 0.4 vCPU) and the same k6 user loop. Plain Next.js holds users. The same box serves with a cache in front of Next.js, with Express on Bun, and 30,000+ with Rust.

The leaderboard

A score is the most simulated users that pass a 5-minute hold with p95 under 500 ms, p99 under 1 s and under 1% errors, the same pass rule as the video this follows. One user browses the feed, opens a post, sometimes likes it or posts, with think time in between: about 0.09 page requests per second each.

What one page view costs

Every server-rendered box was CPU-bound at its score, so the score is almost exactly the CPU budget divided by the CPU each request burns. Dividing the web box's CPU under load by the requests it served gives that cost directly.

Why the numbers differ

All the server-rendered variants do the same useful work: one HTTP call to the API, then HTML for 20 posts. The differences come from what each framework does on top of that, on every request.

1. The work is in the renderer, not the data

The Rust API answers the feed in about a millisecond and serves roughly 39,000 feeds a second on a full core. At every server-rendered frontend's limit it used 3-14% of its 0.4 vCPU; only the stacks above 15,000 users pushed it to 20-50%. The original video's lesson was that a fast backend moves the bottleneck to the database; here the database and API are cheap, so the bottleneck is the HTML renderer.

2. The baseline: what Node itself costs

Express + EJS runs on the same Node 24 as the JS frameworks. Its templates compile once to plain JavaScript functions and a render is string concatenation: no component tree, no serialized data for hydration, no streaming. It costs about ms of CPU per request and holds users. Anything a JS framework spends above that is the framework.

The template engine matters too. The same Express app with Nunjucks (Jinja2-style templates) held users. Rendering the feed page alone took Nunjucks about 0.08 ms of CPU against 0.17 ms for EJS: Nunjucks compiles the whole page, includes and all, into one function, while EJS goes through its include machinery for each of the 20 post partials on every render.

3. React Server Components cost the most

Next.js App Router renders a page twice over: React renders the server components to the RSC payload (a serialized component tree), then renders that payload to HTML, and inlines the payload into the page so the browser can hydrate. The feed page is about 46.6 KB, of which about 28 KB is that payload, and Next.js gzips every response in Node by default. It used about ms per request, roughly × Express.

React itself isn't the problem: Remix (React Router 7) and TanStack Start render the same React components in one streaming pass, embed a 7 KB data blob instead of a component tree, and hold and users, about 5× Next.js. Profiling Next.js itself showed that rendering proper (RSC, HTML, decoding the payload) is only about a quarter of its CPU; the rest is stream plumbing between web and Node streams (22%), sockets (12%), garbage collection (11%) and per-request orchestration. The section Five ways to make Next.js serve more puts every lever side by side.

4. Caching Next.js: 7× inside the framework, 24× in front of it

Three cached builds of the same Next.js app, plus one cache outside it, all measured the same way:

  • Runtime data cache ( users): post pages stored after their first visit, but the feed page is still rendered on every request. Caching the data saved the API call, which was never the expensive part.
  • Full cache (): the whole feed page stored and refreshed every 30 s, post pages stored until edited, nothing forced by likes or new posts.
  • Smart cache (): the same, with the feed refreshed every 15 s and like counts fetched by the browser straight from the API.
  • nginx microcache (): the unmodified app behind nginx in the same 0.4-vCPU box. Anonymous feed pages are cached for 1 s and post pages for 5 s; signed-in users, writes and RSC requests go straight through. nginx answers a hit in C without waking Node, so Node renders about one feed a second plus a few new posts. This is the biggest single gain for Next.js, but it only works because pages are the same for every anonymous visitor and may be up to a few seconds stale.

Smart and full cache (inside Next.js) land in the same place, so the live like counts cost the web server nothing: those requests go to the API box. What stops both near 3,500 is not the cached pages themselves. Measured on one core, serving a stored feed page costs Next.js about 0.40 ms of CPU, the same as Express rendering the page from scratch (0.41 ms) and about 13 times less than an uncached Next.js render (5.3 ms). At their limits, though, the cached builds spent and ms per web request, against Express's ms. The difference comes from the work around the cache hits:

  • Every new post is a full render. Users create a few posts a second; each new post's page is rendered the first time someone opens it, and several users often open it at once. The feed page is regenerated in the background on its timer too.
  • Writes go through route handlers, which cost Next.js about 0.56 ms per like against 0.11 ms in Express.
  • Pages are about three times larger (39 KB vs 12 KB): the cached feed still carries the React Server Components payload for hydration.
  • The failures were in the tail. The cached builds failed on p99 while p95 was still around 300 ms and, for the full cache, while CPU was at 79-98% of the vCPU. Each render, regeneration or garbage collection (the heap reached about 500 MiB) blocks Node's single thread for milliseconds, and the slowest 1% of requests queue behind it. Express does almost no work besides rendering short strings, so its p95 and p99 rise together.

One more effect applies to every Node server here: CPU per request is not a constant. Requests that arrive sparsely cost 2-4× more CPU each than requests that arrive in a stream, because a busy event loop handles several per wake-up. Express went from 0.95 ms per request at 4,700 users to 0.60 ms at 8,000. The CPU-per-request chart above is taken at each stack's own limit, where that effect is roughly comparable.

5. Compiled string renderers sit near the top

SolidStart compiles components to string templates with hydration keys and fills in the values; there is no virtual DOM on the server. It is the fastest framework that hydrates, at users. SvelteKit also compiles to string building. It first held only ; one moved line (section 8) took it to , ahead of SolidStart.

5b. Islands: HonoX hydrates only what moves

HonoX is Hono's metaframework: file-based routes, the same hono/jsx string rendering as plain Hono, and islands, components that hydrate in the browser while the rest of the page stays static HTML. Here the like button is the island; the feed, cards and forms ship no JS. On Bun it held users at ms per request, the best of every stack that hydrates (Leptos in Rust: ), about 32× Next.js and 5× SolidStart.

Against plain Hono JSX on Bun ( users, ms) it costs about 0.1 ms more per request: each of the 20 cards is wrapped in an island element with its props serialized for the browser (2.9 KB more per feed page), and HonoX's production build puts its app inside a second Hono app, so every request is routed twice and passes through the renderer and middleware layers. That is the price of hydration done narrowly: a third fewer users than no hydration at all on the same runtime. On Node, the React frameworks hold 72-95% fewer users than Express does.

One 2-minute run at 10,000 users failed on p99 (4.2 s) with p95 at 36 ms: the server stalled once for a few seconds and its memory jumped from 71 to 280 MiB. The retest at 10,000 and every run up to 16,100 passed with p99 under 160 ms, so the score comes from the retest; above 16,100 it collapsed the same way plain Hono and Express on Bun did past their limits.

6. Serializing state for the browser is not free

Qwik's resumability means the server serializes component state into the page (about 12-13 KB on the feed, a 36 KB page) so the browser never re-runs components. That moves work from the browser to the server: users. Nuxt renders Vue to a string and embeds a 4 KB payload, and runs its data fetch through Nitro's in-process API handler: .

7. Angular emulates a DOM on the server

Angular SSR builds a server-side DOM for each request, then serializes it to HTML, adding hydration annotations, event-replay scripts and the HttpClient transfer cache. Building and walking a document tree is much heavier than appending strings: users, next to Next.js at the bottom.

8. Profile before you rewrite

Where a stack scored far below stacks doing similar work, we profiled it and shipped one idiomatic fix. The originals stay in the leaderboard next to the fixed versions.

SvelteKit had passed users for 2 minutes but held only for 5, with memory climbing to MiB. The cause was a new Intl.DateTimeFormat for each of the 20 post cards on every page; building one loads ICU locale data. Creating it once per process more than doubled both SvelteKit and Astro. None of these fixes changes what the page does; they remove work nobody asked for, so a profiler is worth running before choosing a new framework.

9. Server templates in other languages

The non-JS stacks render HTML templates and stop: no hydration data at all. Within that group, the spread comes from how templates are executed and how requests are served.

  • Rust Axum + Askama held the 30,000-user cap at only % of its vCPU, about ms per request. Askama turns templates into Rust code at build time, so a render is writing into one pre-sized buffer. Projected from that run, its CPU reaches 95% near 52,000 users, memory (~33 KB per open connection) near 58,000, and the shared API near 56,000: about 50,000, an estimate, not a measurement.
  • Go html/template held and failed at 19,500 with its CPU at 100%. Its templates escape values by reflection at run time, so it costs more per request than Askama ( ms), but still less than any JS stack on Node.
  • Leptos () is the full-stack Rust counterpart to Next.js: it hydrates in the browser via WASM, and still serves 31× Next.js.
  • Phoenix () renders HEEx into iodata lists that the VM writes to the socket without building one big string.
  • ASP.NET Core Razor compiles views to C# at build time and held , once idle thread-pool spinning was turned off.
  • Spring Boot + Thymeleaf held , and with the JDK's AOT cache: a fresh container otherwise spends its first minutes JIT-compiling.
  • Flask and Django run 3 blocking gunicorn workers; Django's middleware, CSRF cookie and template engine cost about twice Flask's CPU. Both lost CPU to the 2-second healthcheck recompiling Python's standard library; precompiling it (and Jinja2 for Django) gave and .

10. Not rendering on the server at all

The static build serves 7 KB HTML shells and JS from nginx, and the browser renders from JSON. We ran it once at 30,000 users instead of searching: p95 was 41 ms with nginx at 67% of its vCPU and the API at 47%, so nginx would reach its limit near 42,000 users and the API near 60,000. The server does almost no work per view. The cost moves to every visitor's device, the first view needs the JS before anything shows, and crawlers get an empty shell. That trade-off, not raw capacity, is the real decision.

Is it RAM? No: it's CPU

At their scores the slowest stacks used a fifth to a third of their 2 GB (Next.js about MiB, Angular about MiB) while their CPU sat at 95-100% of the vCPU. Nothing swapped (the box has no swap), nothing was killed for running out of memory, and failures came from latency, not errors. A memory-bound server shows the opposite pattern: memory near the limit, garbage collection eating CPU, then crashes or errors. Adding RAM to these servers would buy nothing; only more CPU, or a renderer that spends less of it per page, moves the number.

The SvelteKit and Astro processes that grew to 770-860 MiB were a symptom: a date formatter built per post card filled the heap. Fixed, they used under 370 MiB and held more than twice the users. Rust at 30,000 users used about 1 GB, almost all of it per-connection buffers.

Does the runtime matter? It depends on how heavy the framework is

Four apps were run unchanged on Node and on Bun 1.4.3 (Next.js also on Deno 2.9):

Bun's HTTP server, its fetch and its stream handling are native code (Zig), so the time a request spends outside the app's own JavaScript shrinks. For Express and Hono that time was most of the request, because their rendering is cheap string building: they gain about 2.6-2.9×. For Next.js and React Router the render itself dominates, and it is the same JavaScript on either runtime: they gain 1.04-1.4×. Deno runs Next.js through its Node compatibility layer and gained nothing.

Bun also reads 90-100% CPU well before its real limit, so for the Bun stacks latency, not the CPU column, told us where the limit was.

Five ways to make Next.js serve more

Take the plain Next.js app ( users) as the centre. Every other variant in this benchmark is one of five moves away from it. Best result in each group, as a multiple of plain Next.js:

  1. Tune Next.js itself (no caching, same App Router). Profiling showed Next 16's cacheComponents also turns on cached navigations, so every request ran a staged render plus a second "prefetch" render, both unused on pages that are all request-time data. Turning it off and sending post cards as props (a Client Component) instead of a rendered tree cut instructions per request by a third and the feed page from 45 to 25 KB. Under full load the CPU per request fell from 8.44 to ms and the score rose to users, 1.6×: more than switching to Bun, from two config lines and one "use client". At light load the same change saved only ~15% CPU; the work it removes (extra renders, a 28 KB payload, the garbage they create) grows with load. A Pages Router port used about 43% less CPU in private runs; it was not benchmarked.
  2. Change the runtime. Same code on Bun: 1.4×. On Deno: none. The work is React and Next's own JavaScript, which a faster HTTP layer doesn't remove.
  3. Cache. Inside Next.js (use cache, ISR) up to 7×; the rest of each request (new posts, writes, a 39 KB page, GC pauses) sets a ceiling. An nginx microcache in front: 24×, because a hit never reaches Node. It needs pages that are the same for anonymous visitors and can be a second or a few seconds stale.
  4. Keep React, change the metaframework. React Router 7 and TanStack Start render the same components in one pass with a small JSON blob for hydration: about 5×, with the same React skills and components. Moving React Router to Bun added only 4%.
  5. Change the framework or the language. A server-template stack with no hydration: 19× on Node (Express + Nunjucks), 48-50× on Bun (Express, Hono), 38× in Go, 60× or more in Rust. If the page still needs interactive parts, islands keep most of that: HonoX on Bun hydrates only the like button and serves 32×; Leptos hydrates the whole page from Rust and serves 31×. This is the biggest gain and the biggest rewrite: the page no longer ships React to the browser.

Roughly in order of effort: a config change gives 1.6×, a runtime swap 1.4×, a proxy cache 24× for anonymous traffic, a React metaframework swap 5×, and a rewrite 19-60×. For a Next.js app with mostly anonymous traffic, the proxy cache is the cheapest large win; for logged-in, per-user pages it doesn't apply, and the remaining levers are the framework and the language.

How each stack renders

Method

  • Two simulated $12 droplets in Docker: the Rust + SQLite API and the frontend, each pinned to its own physical core, throttled to 0.4 vCPU (a desktop core is much faster than a shared droplet vCPU) with 2 GB and no swap. k6 ran on separate cores.
  • Every run starts fresh: a new copy of the 50k-user, 500k-post, 2M-like database and a recreated web container.
  • Search: the first stacks used a 20-second probe, ±25% jumps and a 2-minute bisection to 100 users. Later stacks used a bottleneck-guided search: a 2-minute test run, a jump to where the busiest CPU would reach 95%, then ±10% steps (and a fit of latency against load, sim/predict.py, to jump further), falling back to bisection when a jump overshot. Either way, the score is the most users that pass a 5-minute hold; a failed hold steps down 10%.
  • Cap: searches stopped at 16,000 users at first, later 30,000. Stacks still passing at the cap are marked "cap" with an estimate of the real limit from their CPU, memory and the API's headroom.
  • Same app everywhere: feed and post pages, login, likes and posts through forms, JSON routes for the load test; the same markup and stylesheet; no caching except in the variant labelled cached.
  • Framework defaults kept: gzip on in Next.js and Remix, per-request logging in Remix, CSRF tokens in ASP.NET, Django and Laravel, gunicorn's sync workers. These are part of what each stack costs out of the box.

Caveats

  • One host, one run per user count: treat results within about 10% of each other as a tie.
  • CPU per request mixes page and write requests, and is derived from 2-second samples.
  • The first client-side search was invalid (k6 ran out of local ports) and was rerun with a load-generator fix; the servers were never tuned.
  • Two games ran briefly unpinned during the client-side search; the affected runs passed with large margins.
  • Docker's healthcheck runs inside each box's 0.4-vCPU quota every 2 s: about 8-10% of it for Node, Bun and Deno (a fresh node -e fetch), about 3% for curl, 7-21% for Python before the fix. It is the same for every stack in a family, but it shrinks the budget for the cheap stacks most.
