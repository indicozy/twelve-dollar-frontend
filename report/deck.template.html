Results · the React family

Same React, very different results

Next.js App Router renders React Server Components to a serialized tree, renders that to HTML, and inlines the tree in the page. Remix and TanStack Start render the same components in one pass.

Next.js at the centre · plain Next.js = users

Five ways to make Next.js serve more

Tuning Next.js itself (1.6×) beats switching runtime (1.4×). A proxy cache gives 24× for anonymous pages, and the big multiples need a different framework or language.

Caching Next.js

Cache inside Next.js: 7×. In front of it: 24×

Inside Next.js, a stored page is cheap, but new posts, writes through route handlers, 39 KB pages and GC pauses set a ceiling. An nginx microcache (feed 1 s, posts 5 s, anonymous only) answers hits without waking Node at all.

Switching the runtime

Bun: 1.4× for Next.js, 2.6× for Express

Same code, only the runtime changes. Bun's HTTP server and fetch are native code, so it helps most where the app's own work is small: Express and Hono gain 2.6-2.9×. Next.js gains 1.4× and React Router 4%: React's rendering is the same JavaScript on either runtime. Deno: no gain.

Results · other JS frameworks

Compiled string renderers lead

Angular builds a server-side DOM per request. Qwik serializes component state for resumability. Solid and Svelte compile components to string building. SvelteKit and Astro shown after their one-line fix. HonoX (Bun) hydrates only islands: 32× Next.js.

Why · where the CPU goes

What each request pays for

Machinery around React

Next.js: stream plumbing 22%, sockets 12%, GC 11%, actual React rendering ~25%. Plus a ~28 KB inlined RSC payload in a 46 KB page.

A DOM on the server

Angular builds and serializes a document per request, plus hydration annotations and a transfer cache.

State serialization

Qwik writes ~12 KB of component state for resumability; Nuxt, Remix, TanStack and Solid embed 4-7 KB of data.

Strings

Solid, Svelte, EJS, Askama, Razor: compiled templates that append strings. The cheapest way to make HTML.

Odd results

Profile before you rewrite

Each fix is one idiomatic change a team would ship. SvelteKit and Astro built a date formatter for every post card; moving one line more than doubled both.

The other option

Don't render on the server at all

~42k

users, estimated (30,000 measured: p95 41 ms)

Next.js as a static export behind nginx: the server sends 7 KB shells and JSON, the browser renders. At 30,000 users nginx used 67% of its vCPU and the API 47%.

The cost moves to every visitor's device, first paint waits for JS, and crawlers see an empty shell.

Takeaways

What to take from this

The renderer is the bottleneck

With a fast API, the HTML renderer decides how many users a box serves: for Next.js, for Express on Bun, 30,000+ for Rust.

For Next.js: cache in front, or change framework

Tuning gives 1.6×, Bun 1.4×. An nginx microcache gives 24× for anonymous pages; React Router or TanStack 5×; server templates 19-60×.

Profile first

Seven stacks gained 1.1-3× from one fix each: a date formatter, a healthcheck, a JIT warm-up, session files.

Add CPU, not RAM

Every server-rendered stack hit 95-100% CPU with most of its 2 GB unused.
